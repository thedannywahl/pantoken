Les versions cibles sont distinctes : seules les versions vérifiées sont indiquées, et les versions plus récentes que la dernière version vérifiée doivent être examinées. ## Examiner les versions cibles

Le flux de travail hebdomadaire sur les versions cibles ouvre un ticket d’examen pour les nouvelles versions stables de WordPress et les écosystèmes qui déclarent explicitement un pair npm. Pour les autres cibles, les responsables consultent chaque semaine les notes de version officielles de la plateforme et ouvrent manuellement un ticket d’examen ; l’absence de ticket ne signifie pas qu’une nouvelle version est prise en charge. Pour étendre une revendication :

1. Examinez le schéma de sortie de la version ou les modifications d’intégration, ainsi que l’adaptateur indiqué dans ce tableau.
2. Exécutez la commande de compatibilité de l’adaptateur avec la version candidate, par exemple `vp run @pantoken/postcss#check:compatibility -- 8.5.29`. Par défaut, la commande lit chaque entrée `testedVersions` de ce registre ; les environnements jumelés acceptent leurs options complémentaires.
3. Pour les versions candidates découvertes via les flux, utilisez `vp run downstream:test` ; les tentatives échouées sont conservées dans `scripts/release/downstream-compatibility.json`. Après un examen réussi, exécutez `vp run downstream:bless --package @pantoken/name --version x.y.z` pour mettre à jour la revendication.
4. Effectuez une vérification avec l’environnement hôte, le compilateur ou l’outil de compilation réel, à la version minimale et à la nouvelle version. Adaptez le format de sortie actuel si nécessaire ; n’ajoutez pas d’émetteurs parallèles pour les anciens formats.
5. Mettez à jour `scripts/release/target-compatibility.json` uniquement après la réussite des vérifications, puis exécutez `vp run sync:compatibility`, régénérez la documentation API en anglais et ajoutez un changeset. Les versions plus récentes restent en attente jusqu’à l’intégration de cette modification examinée. La documentation localisée est traitée séparément.

## Dépréciations

Jetons supprimés en amont que pantoken fournit toujours sous forme de couche de compatibilité. Chacun reste fonctionnel jusqu’à l’adoption de sa version mineure en amont `Removed in` ; à ce moment-là, la couche de compatibilité est retirée et une version mineure du consommateur est publiée. Une couche de compatibilité redirige vers un jeton `Replacement` ou conserve sa dernière valeur connue.
