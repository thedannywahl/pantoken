# Kompatibilität

Diese Seite dokumentiert, aus welchen Instructure-UI-Quellen dieser pantoken-Build auflöst und welche Verbraucher sie nutzen. Zielversionen werden getrennt betrachtet: Es werden nur verifizierte Releases aufgeführt, und Releases nach dem letzten verifizierten Release müssen geprüft werden. Mit `vp run sync:compatibility` lässt sich die Seite neu generieren; die Prüfung `gate:compatibility` schlägt fehl, wenn sie nicht mehr aktuell ist.

## Ziel-Releases überprüfen

Der wöchentliche Workflow für Ziel-Releases eröffnet einen Review-Issue für neue stabile WordPress-Releases und Ökosysteme mit einer expliziten npm-Peer-Abhängigkeit. Bei anderen Zielen prüfen Maintainer wöchentlich die offiziellen Release Notes der Plattform und eröffnen manuell einen Review-Issue; ein fehlender Issue bedeutet nicht, dass ein neues Release unterstützt wird. So lässt sich eine Kompatibilitätsangabe erweitern:

1. Das Ausgabeschema oder die Integrationsänderungen des Releases sowie den Adapter in dieser Tabelle prüfen.
2. Den Kompatibilitätsbefehl des Adapters mit dem möglichen Release ausführen, zum Beispiel
   `vp run @pantoken/postcss#check:compatibility -- 8.5.29`. Der Standardbefehl liest jeden
   `testedVersions`-Eintrag aus diesem Register; für gekoppelte Umgebungen gibt es ergänzende Flags.
3. Für aus Feeds ermittelte mögliche Releases `vp run downstream:test` verwenden; fehlgeschlagene Versuche bleiben in
   `scripts/release/downstream-compatibility.json` erhalten. Nach erfolgreicher Prüfung `vp run downstream:bless --package @pantoken/name --version x.y.z` ausführen, um die Angabe zu aktualisieren.
4. Eine Prüfung mit dem echten Host, Compiler oder Build-Tool für die Mindestversion und das neue Release ausführen. Falls nötig, das aktuelle Ausgabeformat anpassen; keine parallelen Legacy-Format-Emitter hinzufügen.
5. `scripts/release/target-compatibility.json` erst nach bestandenen Prüfungen aktualisieren, anschließend `vp run sync:compatibility` ausführen, die englischen API-Dokumente neu generieren und einen Changeset hinzufügen. Neuere Releases bleiben ausstehend, bis diese geprüfte Änderung übernommen wurde. Lokalisierte Dokumentation wird separat bearbeitet.

## Veraltete Tokens

Tokens, die Upstream entfernt hat, die pantoken aber weiterhin als Kompatibilitäts-Shim ausliefert. Jeder Shim bleibt funktionsfähig, bis sein `Removed in`-Upstream-Minor übernommen wird. Dann wird der Shim entfernt und ein Minor-Release des Verbrauchers veröffentlicht. Ein Shim leitet entweder an ein `Replacement`-Token weiter oder behält dessen zuletzt bekannten Wert bei.
