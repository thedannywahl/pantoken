Diese Seite dokumentiert die Instructure UI-Quellen, aus denen dieser pantoken-Build aufgelöst wird, und welche Verbraucher sie nutzen. Zielversionen sind separat: nur verifizierte Releases werden beansprucht, und neuere Releases als das zuletzt verifizierte Release müssen überprüft werden. Mit `vp run sync:compatibility` neu generieren; die `gate:compatibility`-Prüfung schlägt fehl, wenn sie abweicht.

## Überprüfung der Ziel-Releases

Der wöchentliche Target-Release-Workflow eröffnet ein Review-Issue für neue stabile WordPress-Releases und Ökosysteme mit explizitem npm-Peer. Für andere Targets prüfen Maintainer wöchentlich die offiziellen Release-Notes der Plattform und eröffnen bei Bedarf manuell ein Review-Issue; ein fehlendes Issue bedeutet nicht, dass ein neues Release unterstützt wird. Um eine Behauptung zu erweitern:

1. Untersuche das Output-Schema oder Integrationsänderungen des Releases und den Adapter in dieser Tabelle.
2. Führe den Kompatibilitätsbefehl des Adapters mit dem Kandidaten-Release aus, zum Beispiel `vp run @pantoken/postcss#check:compatibility -- 8.5.29`. Der Standardbefehl liest jeden `testedVersions`-Eintrag aus diesem Registry; gekoppelte Umgebungen akzeptieren ihre Begleit-Flags.
3. Für durch Feeds entdeckte Kandidaten benutze `vp run downstream:test`; fehlgeschlagene Versuche werden in `scripts/release/downstream-compatibility.json` aufbewahrt. Nach erfolgreicher Überprüfung ausführen: `vp run downstream:bless --package @pantoken/name --version x.y.z`, um die Behauptung zu aktualisieren.
4. Führe mindestens eine reale Host-, Compiler- oder Build-Tool-Prüfung mit dem neuen Release durch. Remappe das aktuelle Ausgabeformat falls nötig; füge keine parallelen Legacy-Format-Emitter hinzu.
5. Aktualisiere `scripts/release/target-compatibility.json` erst nach Bestehen der Prüfungen, dann `vp run sync:compatibility` ausführen, die englischen API-Dokumente neu generieren und ein Changeset hinzufügen. Neuere Releases bleiben ausstehend, bis diese geprüfte Änderung landet. Lokalisierte Dokumentation wird separat behandelt.

## Deprecations

Upstream-Token, die pantoken weiterhin als Kompatibilitäts-Shim ausliefert. Jeder Shim bleibt funktionsfähig, bis sein `Removed in` Upstream-Minor übernommen wird; danach wird der Shim eingestellt und ein Consumer-Minor geschnitten. Ein Shim leitet entweder auf ein `Replacement`-Token weiter oder friert seinen letzten bekannten Wert ein.
