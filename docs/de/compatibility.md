# Kompatibilität

<!-- Generiert von `vp run sync:compatibility`. Nicht von Hand bearbeiten; den Writer ausführen und committen. -->

Diese Seite dokumentiert, aus welchen Instructure-UI-Quellen dieser pantoken-Build seine Daten bezieht und welche Verbraucher sie verwenden. Zielversionen werden separat behandelt: Es werden nur verifizierte Releases angegeben, und Releases, die neuer als das zuletzt verifizierte Release sind, müssen überprüft werden. Mit `vp run sync:compatibility` lässt sich die Seite neu generieren; die Prüfung `gate:compatibility` schlägt fehl, wenn sie nicht mehr aktuell ist.

## Ziel-Releases überprüfen

Der wöchentliche Workflow für Ziel-Releases eröffnet ein Prüfungs-Issue für neue stabile WordPress-Releases und Ökosysteme mit einem expliziten npm-Peer. Bei anderen Zielen prüfen Maintainer wöchentlich die offiziellen Release Notes der Plattform und eröffnen manuell ein Prüfungs-Issue; wenn kein Issue vorhanden ist, bedeutet das nicht, dass ein neues Release unterstützt wird. So lässt sich eine Angabe erweitern:

1. Prüfe das Ausgabeschema oder die Integrationsänderungen des Releases sowie den Adapter in dieser Tabelle.
2. Führe den Kompatibilitätsbefehl des Adapters mit dem möglichen Release aus, zum Beispiel `vp run @pantoken/postcss#check:compatibility -- 8.5.29`. Der Standardbefehl liest jeden `testedVersions`-Eintrag aus diesem Registry; für gepaarte Umgebungen werden die zugehörigen Flags akzeptiert.
3. Verwende für über Feeds ermittelte mögliche Releases `vp run downstream:test`; fehlgeschlagene Versuche bleiben in `scripts/release/downstream-compatibility.json` erhalten. Führe nach erfolgreicher Prüfung `vp run downstream:bless --package @pantoken/name --version x.y.z` aus, um die Angabe zu aktualisieren.
4. Führe eine echte Prüfung mit Host, Compiler oder Build-Tool für die Mindestversion und das neue Release aus. Passe bei Bedarf das aktuelle Ausgabeformat an; füge keine parallelen Legacy-Format-Emitter hinzu.
5. Aktualisiere `scripts/release/target-compatibility.json` erst, wenn die Prüfungen bestanden sind, führe dann `vp run sync:compatibility` aus, generiere die englische API-Dokumentation neu und füge einen Changeset hinzu. Neuere Releases bleiben ausstehend, bis diese geprüfte Änderung übernommen wird. Übersetzte Dokumentation wird separat bearbeitet.

## Veraltete Tokens

Tokens, die Upstream entfernt hat, die pantoken aber weiterhin als Kompatibilitäts-Shim ausliefert. Jedes Token bleibt funktionsfähig, bis sein `Removed in`-Upstream-Minor übernommen wird; dann wird der Shim entfernt und ein Minor-Release für Verbraucher veröffentlicht. Ein Shim leitet entweder an ein `Replacement`-Token weiter oder behält dessen zuletzt bekannten Wert bei.
