यह पृष्ठ Instructure UI के उन स्रोतों का रिकॉर्ड रखता है जिनसे यह pantoken build resolve करता है, और यह भी कि कौन-से उपभोक्ता उनका उपयोग करते हैं। लक्ष्य संस्करण अलग-अलग हैं: केवल सत्यापित रिलीज़ का दावा किया जाता है, और पिछली सत्यापित रिलीज़ से नए रिलीज़ की समीक्षा आवश्यक है। इसे `vp run sync:compatibility` से फिर जनरेट करें; यदि इसमें बदलाव होता है, तो `gate:compatibility` जाँच विफल हो जाती है।

## लक्ष्य रिलीज़ की समीक्षा

साप्ताहिक target-release workflow, नए स्थिर WordPress रिलीज़ और स्पष्ट npm peer वाले ecosystem के लिए समीक्षा issue खोलता है। अन्य लक्ष्यों के लिए, maintainers हर सप्ताह platform के आधिकारिक release notes जाँचते हैं और मैन्युअल रूप से समीक्षा issue खोलते हैं; issue का न होना इस बात का संकेत नहीं है कि नया रिलीज़ समर्थित है। किसी दावे का दायरा बढ़ाने के लिए:

1. रिलीज़ का output schema या integration बदलाव, और इस तालिका में दिए गए adapter की जाँच करें।
2. उम्मीदवार रिलीज़ के साथ adapter का compatibility command चलाएँ, उदाहरण के लिए `vp run @pantoken/postcss#check:compatibility -- 8.5.29`। डिफ़ॉल्ट command इस registry की हर `testedVersions` प्रविष्टि पढ़ता है; जोड़े वाले परिवेशों में उनके companion flags स्वीकार किए जाते हैं।
3. Feed से खोजे गए उम्मीदवारों के लिए `vp run downstream:test` का उपयोग करें; असफल प्रयास `scripts/release/downstream-compatibility.json` में रखे जाते हैं। सफल समीक्षा के बाद, दावे को अपडेट करने के लिए `vp run downstream:bless --package @pantoken/name --version x.y.z` चलाएँ।
4. न्यूनतम और नए रिलीज़ पर वास्तविक host, compiler या build-tool जाँच चलाएँ। ज़रूरत होने पर मौजूदा output format को remap करें; समानांतर legacy format emitters न जोड़ें।
5. जाँचें सफल होने के बाद ही `scripts/release/target-compatibility.json` अपडेट करें, फिर `vp run sync:compatibility` चलाएँ, English API docs फिर से जनरेट करें और changeset जोड़ें। समीक्षा किए गए बदलाव के शामिल होने तक नए रिलीज़ लंबित रहेंगे। स्थानीयकृत दस्तावेज़ों को अलग से संभाला जाता है।

## अप्रचलन

वे upstream टोकन जिन्हें upstream ने हटा दिया है, लेकिन pantoken अब भी compatibility shim के रूप में उपलब्ध कराता है। प्रत्येक टोकन तब तक काम करता रहेगा, जब तक उसका `Removed in` upstream minor अपनाया नहीं जाता; उस समय shim हटा दिया जाता है और consumer minor जारी किया जाता है। Shim या तो किसी `Replacement` टोकन को आगे भेजता है या उसका अंतिम ज्ञात मान स्थिर रखता है।
