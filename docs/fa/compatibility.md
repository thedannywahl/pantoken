این صفحه منابع Instructure UI را ثبت می‌کند که این ساخت Pantoken از آن‌ها استفاده می‌کند و مشخص می‌کند کدام مصرف‌کننده‌ها از آن‌ها استفاده می‌کنند. نسخه‌های هدف جداگانه‌اند: فقط نسخه‌های تأییدشده اعلام می‌شوند و نسخه‌های جدیدتر از آخرین نسخهٔ تأییدشده باید بازبینی شوند. برای بازتولید این صفحه، `vp run sync:compatibility` را اجرا کنید؛ بررسیِ `gate:compatibility` در صورت مغایرت شکست می‌خورد.

## بازبینی نسخه‌های هدف

گردش‌کار هفتگی نسخه‌های هدف، برای نسخه‌های پایدار جدید WordPress و اکوسیستم‌هایی که peer صریح npm دارند، یک issue بازبینی ایجاد می‌کند. برای هدف‌های دیگر، نگه‌دارندگان هر هفته یادداشت‌های انتشار رسمی پلتفرم را بررسی می‌کنند و به‌صورت دستی issue بازبینی می‌گشایند؛ نبودن issue به این معنا نیست که نسخهٔ جدید پشتیبانی می‌شود. برای گسترش یک ادعا:

1. طرح‌وارهٔ خروجی یا تغییرات یکپارچه‌سازی نسخه و آداپتور مربوطه در این جدول را بررسی کنید.
2. فرمان سازگاری آداپتور را با نسخهٔ پیشنهادی اجرا کنید؛ برای نمونه، `vp run @pantoken/postcss#check:compatibility -- 8.5.29`. فرمان پیش‌فرض همهٔ ورودی‌های `testedVersions` را از این رجیستری می‌خواند؛ محیط‌های جفت‌شده پرچم‌های همراه خود را می‌پذیرند.
3. برای گزینه‌های کشف‌شده از فید، از `vp run downstream:test` استفاده کنید؛ تلاش‌های ناموفق در `scripts/release/downstream-compatibility.json` نگه‌داری می‌شوند. پس از بازبینی موفق، برای به‌روزرسانی ادعا `vp run downstream:bless --package @pantoken/name --version x.y.z` را اجرا کنید.
4. بررسی واقعی میزبان، کامپایلر یا ابزار ساخت را روی حداقل نسخه و نسخهٔ جدید اجرا کنید. در صورت لزوم، قالب خروجی فعلی را نگاشت کنید؛ emitterهای قالب قدیمی موازی اضافه نکنید.
5. فقط پس از موفقیت بررسی‌ها، `scripts/release/target-compatibility.json` را به‌روزرسانی کنید؛ سپس `vp run sync:compatibility` را اجرا کنید، مستندات API انگلیسی را دوباره تولید کنید و یک changeset اضافه کنید. نسخه‌های جدیدتر تا زمان ادغام آن تغییرِ بازبینی‌شده همچنان در انتظار می‌مانند. مستندات بومی‌سازی‌شده جداگانه مدیریت می‌شوند.

## منسوخ‌شدن‌ها
