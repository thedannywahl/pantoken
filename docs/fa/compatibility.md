این صفحه منابع Instructure UI را ثبت می‌کند که این ساخت pantoken از آن‌ها استفاده می‌کند و مصرف‌کنندگانشان را مشخص می‌کند. نسخه‌های هدف جداگانه‌اند: فقط نسخه‌های تأییدشده اعلام می‌شوند و نسخه‌های جدیدتر از آخرین نسخهٔ تأییدشده باید بازبینی شوند. با `vp run sync:compatibility` آن را دوباره تولید کنید؛ بررسی `gate:compatibility` در صورت مغایرت شکست می‌خورد.

## بازبینی نسخه‌های هدف

گردش‌کار هفتگی نسخه‌های هدف، برای نسخه‌های پایدار جدید WordPress و اکوسیستم‌هایی که peer صریح npm دارند، یک issue بازبینی ایجاد می‌کند. برای هدف‌های دیگر، نگه‌دارندگان هر هفته یادداشت‌های انتشار رسمی پلتفرم را بررسی می‌کنند و به‌صورت دستی issue بازبینی باز می‌کنند؛ نبودن issue به این معنی نیست که نسخهٔ جدید پشتیبانی می‌شود. برای گسترش یک ادعا:

1. طرح‌وارهٔ خروجی یا تغییرات یکپارچه‌سازی نسخه و adapter این جدول را بررسی کنید.
2. فرمان سازگاری adapter را با نسخهٔ پیشنهادی اجرا کنید؛ برای نمونه
   `vp run @pantoken/postcss#check:compatibility -- 8.5.29`. فرمان پیش‌فرض همهٔ ورودی‌های
   `testedVersions` را از این رجیستری می‌خواند؛ محیط‌های جفت‌شده پرچم‌های همراه خود را می‌پذیرند.
3. برای گزینه‌هایی که از فید شناسایی شده‌اند، از `vp run downstream:test` استفاده کنید؛ تلاش‌های ناموفق در
   `scripts/release/downstream-compatibility.json` نگه داشته می‌شوند. پس از بازبینی موفق، برای به‌روزرسانی ادعا
   `vp run downstream:bless --package @pantoken/name --version x.y.z` را اجرا کنید.
4. بررسی یک میزبان واقعی، کامپایلر یا ابزار ساخت را روی حداقل نسخه و نسخهٔ جدید اجرا کنید. در صورت نیاز، قالب خروجی فعلی را نگاشت کنید؛ emitterهای موازی برای قالب‌های قدیمی اضافه نکنید.
5. فقط پس از موفقیت بررسی‌ها، `scripts/release/target-compatibility.json` را به‌روزرسانی کنید؛ سپس
   `vp run sync:compatibility` را اجرا کنید، مستندات API انگلیسی را دوباره تولید کنید و یک changeset اضافه کنید. نسخه‌های جدیدتر تا زمان ادغام تغییر بازبینی‌شده در انتظار می‌مانند. مستندات محلی‌سازی‌شده جداگانه مدیریت می‌شوند.
