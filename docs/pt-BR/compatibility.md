Esta página registra as fontes do Instructure UI que esta build do pantoken resolve e quais consumidores
as utilizam. Versões-alvo são separadas: apenas releases verificadas são reivindicadas, e releases mais recentes que
a última release verificada precisam de revisão. Regenerar com `vp run sync:compatibility`; o
cheque `gate:compatibility` falha se houver divergência.

## Revisando releases alvo

O fluxo semanal de releases alvo abre uma issue de revisão para novos releases estáveis do WordPress e
ecossistemas com um peer npm explícito. Para outros alvos, os mantenedores verificam as notas de release oficiais da plataforma semanalmente e abrem uma issue de revisão manualmente; a ausência de uma issue não significa que um novo release
é suportado. Para estender uma claim:

1. Inspecionar o esquema de saída do release ou mudanças de integração e o adaptador nesta tabela.
2. Executar o comando de compatibilidade do adaptador com o release candidato, por exemplo
   `vp run @pantoken/postcss#check:compatibility -- 8.5.29`. O comando padrão lê cada
   entrada `testedVersions` deste registro; ambientes emparelhados aceitam suas flags companheiras.
3. Para candidatos descobertos por feed, usar `vp run downstream:test`; tentativas fracassadas são retidas em
   `scripts/release/downstream-compatibility.json`. Após uma revisão bem-sucedida, executar
   `vp run downstream:bless --package @pantoken/name --version x.y.z` para atualizar a claim.
4. Executar um host real, compilador, ou verificação de build no mínimo e no novo release. Remapear o formato
   de saída atual se necessário; não adicionar emissores legados paralelos.
5. Atualizar `scripts/release/target-compatibility.json` somente após os cheques passarem, então executar
   `vp run sync:compatibility`, regenerar a documentação da API em inglês e adicionar um changeset. Releases mais novos
   permanecem pendentes até que essa mudança revisada seja aplicada. Documentação localizada é tratada separadamente.

## Deprecações

que seu `Removed in` upstream minor seja adotado, ponto em que o shim é aposentado e uma minor do consumidor
é cortada. Um shim redireciona para um token `Replacement` ou congela seu último valor conhecido.
