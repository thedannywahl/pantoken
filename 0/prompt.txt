## 2. The i18n translation workflow

Scripts live in `/Users/dwahl/Scripts/pantoken/docs/scripts/`:

- **`api-translation.ts`** — the adapter architecture. Interface `TranslationAdapter` (`translateMarkdown` / `translateText` / optional `translateBatch`). Two implementations:
  - `GlossaryTranslationAdapter` (`name = "glossary"`, the CI-safe default) — applies `SORTED_REPLACEMENTS`, a fixed ~55-term glossary of TypeDoc structural words (Parameters→Paraméterek, Returns→Visszatérés, etc.). Preserves fenced/inline code and `@scope/pkg` names. **Does not translate prose.**
  - `ClaudeCodeTranslationAdapter` (`name = "claude-code"`) — shells out to `claude -p`, real translation, with code/package placeholder protection and JSON batch mode.
  - `createTranslationAdapter()` picks via `DOCS_TRANSLATION_ADAPTER` env (default `glossary`).
- **`translation-memory.ts`** — content-addressed cache (`TranslationMemory`, `keyFor` = sha256 of kind+source, `translateUnits`). Committed cache dir `docs/i18n-cache/` (`hu.guides.json`, `hu.api.json`). Only new/edited units reach the adapter; markdown translated per-file, short labels batched.
- **`build-api-locales.ts`** — regenerates EN API (TypeDoc → `style-api-badges.ts` → `write-api-overview.ts`), builds CSS API, **clones `docs/api` → `docs/hu/api`**, then runs the adapter over every `.md` and every `typedoc-sidebar.json` label. This is where the API/CSS prose translation would plug in.
- **`translate-guides.ts`** — translates `docs/guide/*.md` → `docs/&lt;locale&gt;/guide/`. Same adapter selector. This is a **manual, committed** workflow.
- **`check-locale-parity.ts`** — asserts HU guide + API trees mirror root page-for-page.

**Relevant package.json scripts** (`docs/package.json`):
- `docs:api:locales` → glossary (default); `docs:api:locales:claude` → `DOCS_TRANSLATION_ADAPTER=claude-code`
- `docs:guides:locales` → glossary; `docs:guides:locales:claude` → claude-code
- `docs:check:locales`, `docs:build`, `docs:build:claude`
- Root `package.json` proxies: `docs:dev`, `docs:build`, `docs:api`.

## 3. Guides vs API/cssdoc prose — what's actually translated

This is the crux. **Both trees run through the same pipeline, but with different adapters in practice:**

- **Guides** — the committed `docs/hu/guide/*.md` are **real Hungarian prose** (verified: `docs/hu/guide/packages.md` opens "# A csomagtérkép / A pantoken egy monorepo…"). Produced by the **claude-code** adapter. `hu.guides.json` holds 7 full-page translations.
- **API (TypeDoc) + CSS (cssdoc) prose** — committed `docs/hu/api/**` is **glossary output only**. Verified against `docs/hu/api/css/button.md` vs `docs/api/css/button.md`: only structural labels changed (`Source`→`Forrás`, `Examples`→`Példák`, `Description`→`Leírás`). The actual prose is still English — component description, the Accessibility paragraph, modifier descriptions ("An AI action.", "A destructive action."), and even section headings `Accessibility` / `Usage` / `Demo` / `Modifiers` (these cssdoc headings aren't in the glossary at all — confirmed no match in `api-translation.ts`).
- `hu.api.json` has ~1,130 entries, but they're glossary-processed markdown/labels (mostly-English bodies), not real translations.

**Why:** `docs/conventions/build-and-docs.md` "Adapter split" — "Hand-written guides use the `claude-code` adapter; the generated API tree (TypeDoc + CSS reference) uses the deterministic `glossary` adapter. Don't run `:claude` over the whole API tree — a cold cache means hundreds of sequential `claude -p` calls."

So the scoping gap is deliberate: nobody wanted hundreds of sequential Claude calls in the build. The pipeline already *supports* claude-code for the API tree (`docs:api:locales:claude` exists); it's just not used because of cost/latency, and the incremental memory only helps after the first expensive full run.
