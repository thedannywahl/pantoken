## Testing infrastructure in the pantoken monorepo

### 1. Test runner and config

The repo uses **vite-plus** (the `vp`/`vpr`/`vpx` CLI, package `vite-plus`), which wraps **Vitest 4.1.10** under the hood. Tests import from the `vite-plus/test` entry point, which is a thin re-export of vitest:

- `/Users/dwahl/Scripts/pantoken/node_modules/vite-plus/dist/test/index.d.ts`:
  ```ts

  export * from 'vitest';
  ```

Every test file does `import { expect, test } from "vite-plus/test";`. There is no standalone `vitest.config.*` — test config lives in the root `/Users/dwahl/Scripts/pantoken/vite.config.ts` under the `test` key (via `defineConfig` from `vite-plus`):

```ts
export default defineConfig({
  test: {
    include: [
      "packages/**/*.{test,spec}.?(c|m)[jt]s?(x)",
      "formats/**/*.{test,spec}.?(c|m)[jt]s?(x)",
      "renderers/**/*.{test,spec}.?(c|m)[jt]s?(x)",
      ...
    ],
  },
```

**Naming/location convention:** `*.test.ts` / `*.test.tsx` (also `.spec`), living in a per-package `tests/` directory (e.g. `formats/components/tests/`, `renderers/web-components/tests/`). The many `vite.config.ts` files under each package configure `pack`/`lint`/`run` tasks, not test settings — test include globs are centralized in the root config only. ### 3. How `vp` runs tests

Each package's `package.json` has a `test` script that calls `vp test`. Examples:
- `formats/components/package.json`: `"test": "vp run @pantoken/plugin-theme-custom-media#build &amp;&amp; node scripts/component-styles.ts &amp;&amp; vp test"`
- `renderers/web-components/package.json`: `"test": "vp test"`

Repo-wide orchestration is in the root `vite.config.ts` `run.tasks` block. The `test:all` task runs tests across every workspace after the build:
```ts
"test:all": {
  command: "vp run -r test",
  dependsOn: ["build:all"],
},
```
It's wired into the `ready:all` aggregate gate (`vp run ready:all`, the root `ready` script) alongside `check:all`, lint, etc. CI runs it too (`docs/conventions/build-and-docs.md`, lines 17/25/37 reference the `test` job in the CI workflow). `docs/conventions/build-and-docs.md` documents the task DAG but has no dedicated "how to run a single test" section beyond that.

### 4. Snapshot tests / fixtures: none

There are **no snapshot tests anywhere** — no `toMatchSnapshot`/`toMatchInlineSnapshot` usages, no `__snapshots__` directories, and no `.snap` files in the repo (worktrees excluded). Instead of snapshots, CSS assertions use substring matching against normalized CSS strings. The normalization helper is `/Users/dwahl/Scripts/pantoken/formats/components/tests/_css.ts`:
```ts
export const norm = (css: string): string =&gt;
  css.replace(/\s+/gu, " ").replace(/\(\s+/gu, "(").replace(/\s+\)/gu, ")")
     .replace(/\s*,\s*/gu, ",").trim();
```

### 5. What `formats/components` and `renderers/web-components` test today

**`formats/components/tests/`** (three files, all pure string assertions on generated CSS — no DOM):
- `sheets.test.ts` — the largest. Calls the `xxxCss()` builder functions (`buttonCss`, `componentsCss`, `proseCss`, etc.), then asserts the returned CSS *string* contains expected selectors/declarations, e.g. `expect(buttonCss({ prefix: "instui" })).toContain(".instui-button")`. Also checks token-reference drift against the token IR via `unknownReferences(...)`, prefix handling, the `SENTINEL` prefix placeholder, RSCSS naming, `@scope`/`@supports`/`popover` structure, etc.
- `parity.test.ts` — iterates the `COMPONENTS`/`UTILITIES`/`RULES`/`DECLARATIONS` registries and asserts each `Definition` emits exactly one well-formed `@cssdoc/core` record with no token drift, using helper `tests/_validate.ts` (which uses `parseCssDocs` from `@cssdoc/core` and `CssDocConfigFile.loadForFolder`).
- `public-surface.test.ts` — freezes the barrel's exported name set (`Object.keys(api).sort()` equals a hardcoded `EXPECTED` list) plus a type-level check of the options interfaces.

**`renderers/web-components/tests/index.test.ts`** (one file) — tests pure helpers and registration logic only: `resolveSpace`/`spacingValue` (from `src/lib/helpers.ts`), `iconSvg`, and `register()` with a stubbed `HTMLElement` + fake registry to assert which custom-element tags get defined (default `instui-` prefix, custom prefix, `only` subset, nested-dependency ordering). No rendering, no shadow DOM, no computed styles.

### 6. Computed-style / `getComputedStyle` / CSS-value assertions: none

There are **zero** `getComputedStyle` calls and no computed-style assertions anywhere in the test suite. All "CSS value testing" is done by asserting substrings on the emitted CSS *source strings* produced by the `xxxCss()` builders (as in `sheets.test.ts`) — never by rendering into a DOM and reading resolved styles. This is the exact gap your proposed DOM-based tests for `formats/components` would fill: today the tests prove the CSS text contains a rule, but nothing proves the browser resolves those custom properties and cascade to the intended computed values.
