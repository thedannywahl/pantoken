### 2. The copy button's click handler — global delegated listener, DOM-agnostic

`.../vitepress/dist/client/app/composables/copyCode.js:4-39` — `useCopyCode()`:

```js
window.addEventListener('click', (e) =&gt; {
  const el = e.target;
  if (el.matches('div[class*="language-"] &gt; button.copy')) {
    const parent = el.parentElement;
    const sibling = el.nextElementSibling?.nextElementSibling; // &lt;pre&gt; tag
    ...
    const clone = sibling.cloneNode(true);
    ...
    let text = clone.textContent || '';
    const lang = /language-(\w+)/.exec(parent.className)?.[1] || '';
    if (isShell(lang)) text = text.replace(/^ *(\$|&gt;) /gm, '').trim();
    copyToClipboard(text).then(() =&gt; { el.classList.add('copied'); ...});
  }
});
```

Registered exactly once, for the app's lifetime, in `dist/client/app/index.js:6,45` — inside the root `VitePressApp` component's `setup()` (comment: `// setup global copy code handler`), alongside `useCodeGroups()`.

**This is a real `window`-level delegated listener using `Element.matches()`** — it has zero knowledge of how the matching DOM got there. It doesn't care whether the `&lt;div class="language-*"&gt;` came from pre-rendered markdown HTML or was rendered at runtime by any Vue component. **Answer to your question (a): yes, it will fire correctly for a Vue-rendered structure**, provided the DOM shape matches exactly:

- Element clicked must satisfy `div[class*="language-"] &gt; button.copy` (direct child, not just descendant).
- `parent.className` must contain `language-&lt;lang&gt;` (used only to special-case shell prompts).
- Critically: `el.nextElementSibling.nextElementSibling` must be the `&lt;pre&gt;` element — i.e., **the button must be followed by exactly one sibling before the `&lt;pre&gt;`** (the `&lt;span class="lang"&gt;`, even if you don't need/want a visible label — you can render it empty/hidden but it must occupy that sibling slot, or the copy handler will grab the wrong node or `undefined`).
- `copyToClipboard` (same file, lines 42-77) does `navigator.clipboard.writeText`, falling back to a `document.execCommand('copy')` textarea hack — same behavior as your current bespoke button, no VitePress-specific state needed.
- Visual feedback (`.copied` class, tooltip swap) is handled purely via CSS (`data-copied` attribute + `::before` content), not JS — see §4.

### 3. Shiki highlighting — Node-only, not reusable client-side without adding a new dependency

`.../vitepress/dist/node/chunk-B0BRqWJx.js:21544-21677` — `async function highlight(theme, options, logger)` calls `createHighlighter(...)` (imported from `shiki`, confirmed via `grep -n "shiki\|createHighlighter" chunk-B0BRqWJx.js:29-30`) and `highlighter.codeToHtml(str, {...})`. This whole function is `async`, uses dynamic `highlighter.loadLanguage(...)`, and is invoked from the markdown-it config pipeline during the Node build — it's never bundled into `dist/client`:

```
grep -rl "shiki" dist/client → only dist/client/theme-default/styles/components/vp-code.css
```

That CSS file (`.shiki span { color: var(--shiki-light/dark, inherit) }`) is pure CSS reading inline custom-properties Shiki injects per `&lt;span&gt;` — no JS. So Shiki's runtime footprint on the client is **zero**; it's exclusively a devDependency-side, build-time tool.

Confirmed in `vitepress`'s own `package.json`: `shiki@^4.4.1`, `@shikijs/core`, `@shikijs/transformers`, `@shikijs/types` are all under vitepress's **regular `dependencies`**, and none appear anywhere in `dist/client`. In this repo's own manifests, `docs/package.json` has no `shiki`/`@shikijs/*` entry at all (only `vitepress: catalog:` at `docs/package.json:59`); `pnpm-lock.yaml` shows `shiki@4.4.1` and the `@shikijs/*` family only as **transitive** entries pulled in by vitepress itself (lines ~4736-4780, ~8257, ~11176+), not as a direct project dependency.

**Answer to (b):** Using Shiki client-side for the dynamic snippet would be a genuinely new client-bundle addition, not "free" — you'd need to add `shiki`/`@shikijs/*` directly to `docs/package.json` and call `createHighlighter`/`codeToHtml` yourself in the Vue component (Shiki does support browser/WASM usage, but it's still extra weight: the oniguruma/JS regex engine plus per-language grammar JSON, easily tens to a couple hundred KB depending on how many languages/themes you load and whether you use the WASM or pure-JS engine, fetched async). It is *not* pulled in "free" by vitepress's own client build, because vitepress's client only needs the CSS variables Shiki already baked into the pre-rendered HTML at build time — it never re-highlights in the browser.

### Direct answers

**(a) Can you reuse VitePress's real copy-button handler as-is?** Yes. It's a single `window`-level delegated `click` listener (`copyCode.js:7`) registered once for the whole SPA lifetime by the root app (`app/index.js:45`), matched purely by CSS selector (`div[class*="language-"] &gt; button.copy`) and DOM sibling-position (`button.nextElementSibling.nextElementSibling` → `&lt;pre&gt;`). It has no awareness of build-time vs. runtime origin. To use it, your Vue component's render output must exactly match markdown-it's emitted shape: `&lt;div class="language-xxx"&gt;&lt;button class="copy" title="…" data-copied="…"&gt;&lt;/button&gt;&lt;span class="lang"&gt;xxx&lt;/span&gt;&lt;pre&gt;&lt;code&gt;…&lt;/code&gt;&lt;/pre&gt;&lt;/div&gt;` — same tag types, same sibling order (the `span.lang` slot is load-bearing for the sibling-walk even if you hide it), rendered inside a `.vp-doc`-ancestor page so the CSS applies.

**(b) Is client-side Shiki realistically wireable?** Yes it's technically possible (Shiki ships a browser/WASM build), but it's a real new dependency you'd add to `docs/package.json` — not something already riding along in the client bundle. Budget for grammar/theme JSON payload and async `createHighlighter()`/`loadLanguage()` calls; it's comparable in shape to adding a lightweight syntax highlighter, not "turning on a switch."

**(c) Minimal faithful approach:** Reuse the DOM shape from `preWrapperPlugin` (§1) and the `.vp-doc` CSS (§4) as-is — that gets you pixel-identical styling and the working native copy button (§2) for free, with zero new dependencies. The only piece VitePress can't give you for free on dynamic content is the syntax-highlighting `&lt;span&gt;`s themselves (§3): either accept plain/unhighlighted `&lt;code&gt;` text inside the native wrapper (still gets the real copy button + matching visual chrome), or take on Shiki client-side as a deliberate, separately-justified dependency addition if colored tokens are a hard requirement.</result>
