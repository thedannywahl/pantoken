## 2. Component definition &amp; registration

**Tag naming / prefix.** `DEFAULT_PREFIX = "instui"`. `ELEMENTS` is the list of 30 base names (`icon`, `button`, `alert`, …, `date-time-input`). A prefix is **always** applied (custom-element names require a hyphen), so empty/whitespace/null falls back to `instui`. `register(target?, { prefix?, only? })`:
- `tag(base)` = `${prefix}-${base}`.
- A **scoped registry adapter** rewrites the canonical `instui-&lt;base&gt;` literals used internally to the active prefix on both `get` and `define` (`name.replace(/^instui-/u, "")` then re-prefix). This is why every element file can hardcode `"instui-alert"` etc. and still honor `{prefix:"x"}`.
- `withSpacing(ctor)` wraps **every** ctor in `define`, adding universal `margin`/`padding` (+ per-side) handling via `applySpacing` and a per-host `MutationObserver`.
- `only` limits registration to a subset, expanded through `NESTED_DEPS` (`date-input`→`calendar`, `date-time-input`→`date-input`) so cherry-picking still works.
- `register()` returns early (`if (!target || typeof HTMLElement === "undefined") return;`) — the SSR/Node-safe guard.

**The `wrapper` factory** (inside `register`) defines the presentational elements. Key facts for a browser parity harness:
- `constructor` does `this.attachShadow({ mode: "open" })`.
- `static observedAttributes` is a fixed list: `variant, size, shape, value, max, label, pressed, lines, placement, minimized, constrain, src, alt, tip, has-shadow`, plus the invoker attrs.
- `paint()` sets `shadowRoot.innerHTML = \`&lt;style&gt;:host{display:${display}}${css}&lt;/style&gt;${render(this)}\``. `display` defaults to `inline-block` (explicit because custom elements default to `display:inline`, which would collapse internal `width:100%`).
- Re-paints on every `attributeChangedCallback`.

**The `register()` function — full source** is at `src/index.ts` lines 222–403 (quoted key parts):

```ts
export function register(
  target: ElementRegistry | undefined = globalThis.customElements,
  options: { prefix?: string | null; only?: readonly string[] } = {},
): void {
  if (!target || typeof HTMLElement === "undefined") return;
  const wanted = options.only ? withNestedDeps(options.only) : null;
  const prefix =
    typeof options.prefix === "string" &amp;&amp; options.prefix.trim() !== ""
      ? options.prefix
      : DEFAULT_PREFIX;
  const tag = (base: string): string =&gt; `${prefix}-${base}`;
  const host = target;
  const registry: ElementRegistry = {
    get: (name) =&gt; host.get(tag(name.replace(/^instui-/u, ""))),
    define: (name, ctor) =&gt; {
      const resolved = tag(name.replace(/^instui-/u, ""));
      if (!host.get(resolved)) host.define(resolved, withSpacing(ctor));
    },
  };
  // …syncInvoker, wrapper, variantClass, onCommand defined here…
  const I = { prefix: "instui" } as const;
  const ctx: RegisterContext = {
    registry, tag, I, invokerSupported: INVOKER_SUPPORTED,
    onCommand, wrapper, variantClass, iconSvg,
  };
  for (const def of DEFINITIONS) {
    if (wanted &amp;&amp; !wanted.has(def.name)) continue;
    def.define(ctx);
  }
}
register(); // auto-register; no-op in Node
```

## 3. Variant/state surface — how consumers select variants

Variants are selected almost entirely by **HTML attributes on the host**, which the render function maps to `.instui-*` classes with `-modifier` fragments inside the shadow root. There are no reflected IDL properties for variants; state re-paints via `attributeChangedCallback`.

- **`variant` → `-color-&lt;variant&gt;`**, via `ctx.variantClass(name, host)`:
  ```ts
  const variantClass = (name, host) =&gt; {
    const variant = frag(host.getAttribute("variant"));
    return variant ? `instui-${name} -color-${variant}` : `instui-${name}`;
  };
  ```
  `frag()` sanitizes to `[a-z0-9-]`. So `&lt;instui-button variant="secondary"&gt;` → inner class `instui-button -color-secondary`, which matches `@pantoken/components`' `.instui-button.-color-secondary` selector exactly.
- **Per-element bespoke mappings** (the generic `variantClass` only handles `variant`):
  - `avatar`: `size` → `-size-&lt;size&gt;`, `shape="rectangle"` → `-shape-rectangle`.
  - `img`: `display="block"` → `-display-block`, `constrain` → `-constrain-&lt;value&gt;`.
  - `tray`: `size` → `-size-&lt;value&gt;`.
  - `toggle-button`: `pressed="true"` → renders `&lt;button class="instui-button -toggle" aria-pressed="true"&gt;`.
  - `icon-button`: always `class="instui-button -shape-square"`; `label` → `aria-label`.
  - `alert`: `has-shadow="false"` → appends `-without-shadow`.
- **Behavioral state via `:host([attr])` selectors** in the co-located CSS (drive from the host attribute): e.g. drawer-layout — `:host([placement="end"]) .layout {flex-direction:row-reverse}`, `:host(:not([open])) .tray,:host(:not([open])) .handle {display:none}`, `.handle.-dragging`. Modal drives a real `&lt;dialog&gt;` open/close from the `open` attribute (no CSS state class).

**Important parity gap:** the `wrapper` observes `size`/`shape` but `&lt;instui-button&gt;` itself only wires `variant`. `&lt;instui-button size="small"&gt;` triggers a repaint but produces **no** `-size-sm` class. Size/shape modifiers exist in `@pantoken/components` button CSS (`.instui-button.-size-sm`, `.-shape-square`, etc.) but are only reachable on the web-component for `avatar`/`tray`/`icon-button`/internal calendar buttons — not on the public `&lt;instui-button&gt;`. Worth an explicit test-plan note.

It **reuses the same `-color-secondary` style modifiers as `@pantoken/components`** — it does not have parallel bespoke color CSS. The presentational elements inject the identical builder output.

- The component CSS is entirely **token-referencing**: `formats/components/src/components/button.ts` shows every declaration uses `var(--instui-*)` (e.g. `var(--instui-color-background-interactive-action-primary-base)`, `var(--instui-spacing-space-xs)`). **Where `--instui-*` custom properties come from in a shadow root at runtime:** they are **inherited** custom properties that pierce the shadow boundary. Nothing injects them into each shadow root. **Discrepancy to flag for the plan:** `docs/conventions/web-components.md` claims `register()` also injects `foundationCss()` once into `document.head` as `&lt;style id="pantoken-foundation"&gt;` (elevation + focus declarations). ## 6. JS-behavior tier vs pure CSS

Two tiers (from `docs/conventions/web-components.md` "JS-behavior tier" + code):

**Pure-CSS / presentational** (via `wrapper` or a thin bespoke class, state = attribute → class, re-paint on attr change): `button`, `alert` (has a JS `timeout` timer but visual state is CSS), `badge`, `pill`, `tag`, `avatar`, `spinner`, `progress`, `progress-circle`, `metric`, `rating`, `icon-button`, `toggle-button`, `truncate`, `img`, `side-nav-bar`, `tree-browser`, `icon`.

**Interactive JS behavior** — the consistent declarative driver is the **Invoker Commands API** (light-DOM `&lt;button command="…" commandfor="id"&gt;`), routed by the shared `onCommand(target, handler)` helper, which falls back to a click-delegate on `target.getRootNode()` when `!("command" in HTMLButtonElement.prototype)`:
- `modal` — real `&lt;dialog&gt;`; `open` attribute → `showModal()`/`close()`; native dismissal reflects back to `open` and re-fires a bubbling `close`; custom commands `--show`/`--close`/`--toggle`.
- `popover` / `tray` / `context-view` — native `[popover]` (use `popovertarget`/`command="toggle-popover"`); the shadow `&lt;button&gt;` invoker is bridged to light-DOM targets via `syncInvoker` (mirrors `popovertarget`/`commandfor` onto the inner button's IDL properties, resolving the id against the host's root).
- `drilldown` — stateful multi-level menu; `--goto` (reads `data-page`) / `--back`.
- `pages` — one panel at a time via View Transitions; `--push` / `--back`; slotted `[data-page]` panels, hidden via `::slotted([data-page][hidden]){display:none}`.
- `drawer-layout` — `open` attribute reveals tray; `placement` picks side; drag handle resizes `--drawer-width` (clamped 8–40rem) via pointer capture; commands `--toggle`/`--open`/`--close`.
- `calendar` — interactive month grid; `value`/`view` (`yyyy-mm-dd`) attributes; prev/next/day are `&lt;button&gt;`s driving `--calendar-prev`/`--calendar-next`/`--calendar-select`; selecting sets `value`+`view` and dispatches composed bubbling `change`.
- `date-input` / `date-time-input` — field + calendar-dropdown popover; nest `calendar` (dependency ordering enforced).

**How states are represented in the DOM/shadow** (relevant for your parity reads):
- `open` — host attribute; drives a real `&lt;dialog&gt;` (modal) or `:host([open])` CSS selectors (drawer-layout). Popover/tray use the native popover top-layer.
- `selected` — calendar sets the `value` attribute and re-renders the grid (selected day is a `&lt;button&gt;` with a selected class in its shadow markup).
- `pressed` — toggle-button maps `pressed="true"` to `aria-pressed="true"` on the inner `.instui-button.-toggle` (components CSS keys off `.-toggle[aria-pressed="true"]`).
- `focus` — CSS `:focus`/focus-outline tokens; in headless mode focus events don't fire on `.focus()`, so dispatch a composed `focusin` (per docs).
