## 1. `KIND_GROUPS` and the two functions that consume it

**File:** `node_modules/.pnpm/@cssdoc+markdown@0.7.8/node_modules/@cssdoc/markdown/dist/index.mjs`

`KIND_GROUPS` (lines 31–49) — display order is fixed: component, utility, rule, declaration.

```js
/** Sidebar/index groups, in display order. Only kinds with records appear. */
const KIND_GROUPS = [
  { kind: "component",   label: "Components" },
  { kind: "utility",     label: "Utilities" },
  { kind: "rule",        label: "Rules" },
  { kind: "declaration", label: "Declarations" },
];
```

It is consumed by exactly two exported functions. **The grouping key is `record.kind` in both** — never `group`/`category`.

**(a) Index-page groups — `renderIndex`** (index.mjs lines 305–323):

```js
function renderIndex(entries, options = {}) {
  const baseHref = options.baseHref ?? "/";
  const lines = [`# ${options.title ?? "CSS API reference"}`, ""];
  if (options.intro) lines.push(escProse(options.intro), "");
  for (const group of KIND_GROUPS) {
    const inGroup = entries.filter((e) =&gt; e.kind === group.kind);
    if (!inGroup.length) continue;                    // empty groups dropped
    lines.push(`## ${group.label}`, "", ...table(
      ["Name", "Class", "Summary"],
      inGroup.map((e) =&gt; [
        `[${e.name}](${baseHref}${e.name}.md)`,
        `\`${e.className}\``,
        cell(e.summary),
      ])));
  }
  return `${lines.join("\n")}\n`;
}
```

**(b) Sidebar groups — `buildSidebar`** (index.mjs lines 334–351):

```js
/** Build the sidebar tree (Overview, then a group per kind). */
function buildSidebar(entries, baseHref = "/") {
  const sidebar = [{ text: "Overview", link: baseHref }];
  for (const group of KIND_GROUPS) {
    const items = entries.filter((e) =&gt; e.kind === group.kind).map((e) =&gt; ({
      text: e.name,
      link: `${baseHref}${e.name}.md`,
    }));
    if (items.length) sidebar.push({ text: group.label, collapsed: false, items });  // empty groups dropped
  }
  return sidebar;
}
```

**Signatures** (from `dist/index.d.mts` lines 148–149, 102–103):

```ts
declare function buildSidebar(entries: readonly CssDocEntry[], baseHref?: string): SidebarItem[];
declare function renderIndex(entries: readonly CssDocEntry[], options?: RenderIndexOptions): string;
```

`SidebarItem` (index.d.mts 107–112): `{ text: string; link?: string; collapsed?: boolean; items?: SidebarItem[] }`.

**Grouping logic summary:** both functions iterate `KIND_GROUPS` in its fixed array order; for each group they `entries.filter(e =&gt; e.kind === group.kind)`; a group producing zero records is skipped (`continue` in renderIndex, `if (items.length)` in buildSidebar). No sort within a group (entries arrive already sorted by name — see `BuildCssApiResult.entries` "sorted by name", index.d.mts line 140). Group order and labels are hard-coded in `KIND_GROUPS`; there is no option to reorder or relabel them.

## 2. The `@group` / `@category` tag — definition and current use

**Definition — `@cssdoc/spec`**, `dist/index.mjs` lines 71–79 (inside `CSSDOC_TAGS`):

```js
{ name: "group",    kind: "block" },
{ name: "category", kind: "block", aliasFor: "group" },
```

So `group` is a **block** tag, single-valued (no `allowMultiple`), and `category` is a straight alias of it. The `CssdocTag` shape is in spec's `index.d.mts` (lines 24–37). Mirror definitions/derivations:
- `@cssdoc/core` `ParsedDoc.group` — `dist/lite-CLGf1QSF.d.mts` line 698: `/** @group/@category — a documentation group. */ group?: string;`
- `CssDocEntry.group` — same file, line 454: `/** A documentation group/category, from @group/@category. */ group?: string;`

**Is it rendered / used?** — **Not a pure no-op, but it does NOT drive sidebar or index grouping.** A grep of the markdown runtime for `.group` finds exactly one consumer: the per-page **meta line** in `renderEntry`.

`@cssdoc/markdown/dist/index.mjs` lines 152–157:

```js
const meta = [];
if (entry.since)  meta.push(`**Since:** ${escProse(entry.since)}`);
if (entry.group)  meta.push(`**Group:** ${escProse(entry.group)}`);          // &lt;-- the only use
const src = options.resolveSource?.(entry);
if (src) meta.push(`**Source:** [${escProse(src.label ?? "source")}](${src.href})`);
if (meta.length) lines.push(meta.join(" · "), "");
```

So `entry.group` renders as a `**Group:** &lt;value&gt;` fragment on the fixed header meta line (joined with Since/Source by ` · `). It is **display-only metadata**: it does not feed `buildSidebar`, `renderIndex`, `buildCssApi`, or any sidebar/section grouping. Sidebar and index grouping are driven solely by `record.kind`. (The `RenderEntryOptions` doc comment confirms this — index.d.mts lines 20–23 describe "the Since/Group/Source meta line" as part of the fixed page header.)

Implication for the proposal: `@group`/`@category` is currently free to repurpose for sidebar/index grouping — its only existing behavior is the one-line meta string, which a grouping feature could either keep, subsume, or supersede.

## 5. Render config (`@cssdoc/config`) — is there any group option?

**File:** `@cssdoc/config/dist/index.d.mts`. The `render` block type is **`RenderConfig`** (lines 16–22):

```ts
interface RenderConfig {
  sectionOrder?: readonly string[];
  headingPrefix?: string;

```

Exposed on the loaded config as `CssDocConfigFile.render: Readonly&lt;RenderConfig&gt;` (index.d.mts lines 80–85), merged across the `extends` chain.

The JSON Schema `render` object (`cssDocSchema`, index.d.mts lines 317–342) enumerates exactly the same four keys — `sectionOrder`, `headingPrefix`, `baseHref`, `structureView` — with `additionalProperties: false`. `sectionOrder` controls the reorderable **`##` sections within one record page** (keys from `SectionKey`), not sidebar groups.

**There is no existing option anywhere for sidebar groups, group ordering, or group labels.** The whole kind-grouping (`KIND_GROUPS`) is hard-coded in `@cssdoc/markdown`, and `additionalProperties: false` at both the top level and inside `render` means a new option would need a schema addition. This is the gap the proposal addresses.

## Proposal-relevant conclusions

1. Sidebar and index grouping is **100% driven by `record.kind`** via the hard-coded `KIND_GROUPS` array in `@cssdoc/markdown`, consumed identically by `buildSidebar` and `renderIndex` (fixed order, empty groups dropped, no per-group sort/label/order option).
2. `@group`/`@category` currently drives **only** the `**Group:**` per-page meta-line string (`renderEntry`, markdown index.mjs line 154). It is otherwise unused — safe to repurpose as a grouping key.
3. `CssDocEntry` already carries `group?: string` parsed from the tag, so a grouping feature needs **no new parse field**.
4. The config surface (`RenderConfig`, JSON Schema, both `additionalProperties: false`) has **no group option**; adding group-order/label config would require touching `@cssdoc/config`'s `RenderConfig` + `cssDocSchema`, and the grouping functions in `@cssdoc/markdown` (`buildSidebar`/`renderIndex`), plus threading through `EmitCssApiOptions`/`emitCssApi` like the existing `sectionOrder`/`structureView` defaults.</result>
