# CI restructure plan — pantoken monorepo

## Key repo facts I verified (that shape the design)

- **Task cache** is at `node_modules/.vite/task-cache/v17/*.tar.zst` — inside `node_modules`, which setup-vp's `run-install` populates.
- **Git hooks**: `core.hooksPath = .vite-hooks/_`. That `_/` dir is a husky-style runner, gitignored and regenerated by vp. Human-authored hook bodies live one level up as `.vite-hooks/&lt;name&gt;` (today only `.vite-hooks/pre-commit` = `vp staged`). The `_/commit-msg` dispatcher **already exists** and forwards `$1`, and `_/h` prepends `node_modules/.bin` to PATH. So dropping in `.vite-hooks/commit-msg` is auto-wired — no installer step.
- **cut-release.ts already runs scoped gates** before tagging: `vp run -F &lt;name&gt; build|check|test` over the release set, plus `vp exec -F &lt;name&gt; publint|attw` over the publishable subset. release.yml then redundantly re-runs the full-workspace `ready`+publint+attw.
- **No `...`/closure filter syntax** is used anywhere in the repo — only `-F &lt;exact-name&gt;` and `-F "./glob/**"`. So a docs-subgraph closure filter is unverified.

## 1. New `.github/workflows/ci.yml` (pull_request + push to main)

Decision on the core question: each split job **does** pay its own setup-vp install (unavoidable). Rather than upload/download gitignored generated dirs (brittle — 9 roots to enumerate), use **one `build` job that saves the vp task-cache**; downstream jobs restore it and replay `vp run -r build` as a near-instant cache hit to materialize generated artifacts. `build` has no `needs`; `typecheck`/`test`/`lint`/`gates-publint`/`gates-attw` all `needs: build` so they start warm (no cold-build stampede). `commitlint` is independent.

- `concurrency: { group: ci-${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: ${{ github.event_name == 'pull_request' }} }`
- The union of jobs equals `ready` + publint + attw, parallelized; `ready` itself is never invoked.

**Cache config** (path is just the one subtree, restored AFTER setup-vp so install can't clobber it):
- Path: `node_modules/.vite/task-cache`
- build job `actions/cache@v4` (read+write) key: `vp-taskcache-${{ runner.os }}-${{ hashFiles('pnpm-lock.yaml','vite.config.ts') }}-${{ github.sha }}`
- restore-keys: the same-minus-sha prefix, then `vp-taskcache-${{ runner.os }}-`
- downstream jobs use `actions/cache/restore@v4` (read-only) with the same sha key (exact hit from build's save) + restore-keys fallback.

Rationale: the vp cache is internally content-addressed by task inputs, so a stale restore only yields misses (never wrong). The lockfile/config hash bounds cache growth; the sha makes each run write an immutable entry.

Job shape (downstream): `checkout → setup-vp → cache restore → vp run -r build → &lt;its task&gt;`. `lint` runs `lint:css`, `lint:js`, `validate:generated:only`, `lint:markdown` in sequence. `commitlint` uses `fetch-depth: 0` and `vp exec commitlint --from ${{ github.event.pull_request.base.sha }} --to ${{ github.event.pull_request.head.sha }} --verbose`.

## 2. `.vite-hooks/commit-msg` (new, committed, executable)

```sh
vp exec commitlint --edit "$1"
```

No shebang (runner invokes `/bin/sh -e`), mirroring `pre-commit`. `vp exec` resolves `commitlint` from `node_modules/.bin` — no pnpm. Config already in place (`commitlint.config.ts` → `@commitlint/config-conventional`).

## 3. release.yml — recommend Option (a): scoped verification

Replace the full `vp run ready &amp;&amp; gate:publint &amp;&amp; gate:attw` with verification scoped to exactly the publish set. Reorder so the release-plan step runs first (produces `.release-packages.txt`), then build `-F` filters from it and run `vp run -F.. build|check|test` + `vp exec -F.. publint|attw ...` (the exact scoped forms cut-release already uses). **Leave every provenance step unchanged**: setup-node registry, corepack pnpm, `NPM_CONFIG_PROVENANCE`, `id-token: write`, the publish loop, the GitHub release. Also add the task-cache restore so the scoped build hits main's warmed cache.

**Safety tradeoff**: release.yml stops re-verifying packages outside the release set. That's caught by ci.yml on the merge-to-main that produced the tag, and by cut-release locally. What ships to npm is still verified in-CI against the exact publish set right before publish. Lost coverage ("a non-published package broke") doesn't affect published artifacts.

**Verify**: `.release-packages.txt` is the publishable list; confirm `vp run -F &lt;publishable&gt; build` transitively builds workspace deps so packs are complete — otherwise emit the full release-set list from `plan-package-release.ts` and drive build/check/test from that.

## 4. docs.yml

- **Paths filter**: add `on.push.paths` for `docs/**`, `platforms/**`, `formats/**`, `packages/**`, `renderers/web-components/**`, `plugins/**`, `pnpm-lock.yaml`; keep `workflow_dispatch`. Deliberately broad because the site is themed by generated token output from many packages — broad-but-correct beats minimal-but-stale for a deploy. Skips scripts/tools/root-config churn.
- **Cache**: add the same task-cache restore after setup-vp.
- **Build scoping**: recommend **keeping `vp run -r build`**. The nested-vp constraint isn't the blocker (workflow runs `vp` at top level), but the closure-filter syntax is unverified and a hand-listed `-F` set of docs' ~14 deps risks silently missing a generated dir. With a warm cache, `-r build` is cheap. Only scope later after verifying vp supports a dependency-closure selector.

## Needs runtime verification
1. Task cache survives `run-install` and restore lands before first `vp run -r build` (ordering makes it robust regardless).
2. `vp check` with no `-F` typechecks the whole workspace (parity with `ready`).
3. `vp run -F &lt;publishable&gt; build` transitively builds workspace deps.
4. `vp exec commitlint --from/--to` resolves the bin in CI and lints the range.
5. Any docs subgraph scoping — only if the closure-filter syntax is confirmed.
