## 3. What appears in `@pantoken/css` vs `@pantoken/components`

- **Shipped `@pantoken/css` (`css` export):** base tokens only — **zero plugin output**, because `toCss(tokens)` gets no plugins. Plugin `css`-hook output appears only when a consumer explicitly passes plugins (astro `pantokenCss`, manual `toCss` calls, the plugin docstring examples).
- **`@pantoken/components` sheets:** built on a **separate path** — authored CSS composed via `formats/components/src/lib`, then lowered by the PostCSS `themeCustomMedia` plugin (`component-styles.ts`). They do **not** go through `toCss`'s `css`-hook mechanism. `plugin-colors` helpers are baked into that authored CSS at build time.

So "including css plugins in scope" for the lean sheet is about the **`toCss` `css`-hook path** (the `appendContribution` `@property` branch), not the components pipeline.

## 4. Animatable/typed vs inert plugin properties

- Because no shipped plugin emits `c.properties`, there are currently **no plugin-contributed typed `@property` registrations**. Nothing today "must stay typed."
- All current plugin values flow through `c.declarations` or raw `append`/`prepend`: transition `duration`/`timing` (a `&lt;time&gt;` and a timing function), the `stacking` z-index integers, logo `url(data:…)`, and debug outline rules. These are emitted as plain declarations by design — the transition plugin deliberately chose `declarations` over `properties` even though `--instui-transition-duration` is nominally a `&lt;time&gt;` that could be animated.
- The only reason a custom property *must* be a real `@property` is if it's interpolated/animated/transitioned and needs typed interpolation (a `&lt;color&gt;`, `&lt;length&gt;`, `&lt;angle&gt;`, `&lt;time&gt;` that a keyframe or `transition` animates). No plugin exercises that today.

## Deliverable: what "include css plugins in the scope" should mean concretely

The lean mode flattens the **base loop's** typed `@property` registrations into `:root` declarations. Plugin output is emitted separately by `appendContribution`, whose `c.properties` branch (`to-css.ts:99–104`) still writes `@property` blocks. "Include css plugins in the scope" means:

**In lean mode, route plugin-contributed `c.properties` through the same flatten-to-declaration treatment** — i.e. `appendContribution` should, in lean mode, emit each `PropertyRule` as a `--name: value;` `:root` declaration (merged with `c.declarations`) instead of an `@property` block. Raw `c.prepend`/`c.append`/`c.declarations` are already declaration-shaped and need no change.

Practical notes for the plan:
- **No shipped plugin uses `c.properties`,** so this change is a no-op for the current plugin ecosystem and for the default sheet (which passes no plugins). It matters for third-party/consumer plugins that pass typed properties.
- **This flattening is also a correctness fix:** `appendContribution` currently emits `@property` for plugin properties with a hardcoded `inherits: true` and **no `isContextual` guard**, so a plugin passing a `var()`/`light-dark()` initial-value already produces an invalid `@property`. Lean flattening sidesteps that.
- **"Must stay typed" set is empty today.** If a future plugin needs a genuinely animatable typed property, it would need an explicit opt-out (e.g. a per-property "keep typed" flag), since lean mode's whole point is to drop `@property`. Worth flagging as a design question, but nothing in the repo requires it now.
