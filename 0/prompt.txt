### Feasibility of per-element IIFE outputs

**Is it feasible with the same tool (Vite/Rollup)?** Only by running the build **once per element**, not by giving `vite build()` multiple entries in one call. Vite's `build.lib` mode explicitly disallows multiple entries when `formats` includes `"iife"`/`"umd"` — and even bypassing `lib` mode and going straight to `rollupOptions.input` as a multi-entry object, Rollup itself refuses code-split output in `iife`/`umd` format ("UMD and IIFE output formats are not supported for code-splitting builds") **whenever two entries would share a chunk** (which they would here — every element imports shared context/wrapper machinery from `src/lib/` and `src/index.ts`, and several import `@pantoken/components`/`@pantoken/icons`). So the only workable shape is: `build-iife.ts` loops over `ELEMENTS` (30 entries, `src/index.ts:84-115`) and calls Vite's `build()` **30 separate times**, once per element, each with its own `lib.entry` (a synthetic per-element entry module — e.g. one that imports just `register` and calls `register(customElements, { only: ["alert"] })`) and its own `fileName: () =&gt; "alert.iife.js"`. This is a straightforward extension of the existing single-entry script (`build-iife.ts:17-38`), just wrapped in a `for (const name of ELEMENTS)` loop with `only: [name]` passed through, expanded via the (now-exported, per Part 1) `NESTED_DEPS`/`withNestedDeps` so e.g. `date-time-input.iife.js` also registers `date-input` and `calendar`.

**Would each per-element IIFE duplicate shared internals? Yes, unavoidably, given the current source shape:**
- Since Rollup/Vite can't share chunks across independent IIFE builds, every one of the 30 files would re-bundle: `src/lib/context.ts` (70 lines), `src/lib/helpers.ts` (120 lines), `src/lib/strings.ts` (82 lines) plus all the `register()`/`makeWrapper`/`makeRegistry`/`makeOnCommand`/`withSpacing`/`syncInvoker` plumbing in `src/index.ts` (roughly lines 149–450) — i.e. a fixed multi-KB "runtime tax" repeated 30×.
- **Far more significant:** because `register()`'s `iconSvg` default resolver is wired to `@pantoken/icons` unconditionally at `src/index.ts:20` (not lazily, not injected per-element), **every** per-element bundle that goes through `register()` — which is all of them, since that's the shared registration pipeline — would embed the same ~2.5 MB icon/token payload that's already measured in the current single bundle. 30 × ~2.5 MB ≈ **75 MB** of published `dist/*.iife.js` output, almost entirely duplicate bytes, for elements that mostly don't even render icons (`alert`, `badge`, `pill`, `progress`, etc. — only `icon` and `icon-button`, at `src/elements/icon.ts:29` and via `ctx.iconSvg`, actually call it). This is the single biggest, concrete blocker, not a minor inefficiency.
- Each element's own CSS builder (`alertCss`, `buttonCss`, from `@pantoken/components`, confirmed via `src/elements/alert.ts:1` and `src/elements/button.ts:1`) would tree-shake reasonably well per file since `@pantoken/components`'s `dist/index.mjs` (667 KB) doesn't itself pull in `@pantoken/tokens`/icons (its only imports are `@pantoken/plugin-colors` and `@pantoken/utils`, per its dist file's import lines) — so this part of the duplication concern is real but much smaller than the icon problem.

**What would need to change to make this actually small-per-file (not just "technically 30 files"):**
1. Decouple `iconSvg`'s default resolver from a static top-level import — make it lazy/dynamic (`await import("@pantoken/icons")` only inside the function body, so it's only pulled in by files that actually call it) or make it an injectable/optional dependency that per-element IIFE builds simply omit unless the entry is `icon`/`icon-button` (and anything indirectly nested under them).
2. Accept that some duplication of the small `src/lib/*` runtime plumbing (a few KB) across 30 files is an inherent cost of the iife/no-code-splitting constraint — this is the "note the drawback plainly" part: it's real but modest once the icon problem above is fixed.
3. Decide whether nested-dependency elements (`date-input`, `date-time-input`) get a dedicated combined file (as today's `register({only:[...]})` already supports) or whether their IIFE should also bundle `calendar` inline — i.e. `date-input.iife.js` would need to embed `calendar`'s definition too, duplicating it again versus a hypothetical standalone `calendar.iife.js`.
