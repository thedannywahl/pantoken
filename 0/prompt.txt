## 2. How it derives `path` — the bug

`docs/scripts/cdn-icon-manifest.ts:14-16`:

```ts
// Extract the first &lt;path d="…"&gt; from inline SVG markup.
function extractPath(svg: string): string {
  return /\sd="([^"]+)"/.exec(svg)?.[1] ?? "";
}
```

and used at `docs/scripts/cdn-icon-manifest.ts:26`:

```ts
path: extractPath(icon.svg),
```

`icon.svg` (from `@pantoken/icons`, `formats/icons/src/index.ts:26,64`) already contains the **full, correct multi-element SVG markup** — that part of the pipeline is fine. The bug is entirely in `extractPath`: the regex `/\sd="([^"]+)"/` runs against the whole markup string with no `g` flag and no per-element scoping, so `.exec()` returns only the **first** `d="…"` attribute value found anywhere in the string. It does not concatenate all `&lt;path&gt;` `d` values, and it has no awareness of `&lt;circle&gt;`, `&lt;rect&gt;`, `&lt;line&gt;`, `&lt;polygon&gt;`, or `&lt;ellipse&gt;` elements at all — those are silently discarded, and if the *first* shape element in the markup happens to be one of those (no `d` attribute), the function may return `""` even though later `&lt;path&gt;` elements exist.

The consumer, `docs/.vitepress/theme/components/IconPicker.vue:252-259`, only renders a single `&lt;path :d="icon.path" /&gt;` inside the `&lt;svg&gt;`, so even if the manifest were fixed to concatenate every path's `d`, the picker itself would still need multiple elements (or a merged `d`) to render `&lt;circle&gt;`/`&lt;rect&gt;`/`&lt;line&gt;` shapes — currently it can only ever show path data.
