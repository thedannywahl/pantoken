## 1. How translation actually happens

`/Users/dwahl/Scripts/pantoken/docs/scripts/translation-memory.ts` is **not** a translation engine itself — it's the shared batch driver + content-addressed cache facade that both docs pipelines (guides and API) use. It calls out to a pluggable `TranslationAdapter` (defined in `docs/scripts/api-translation.ts`), which is where the actual translation happens:

- **`GlossaryTranslationAdapter`** (`docs/scripts/api-translation.ts:160`) — deterministic, keyless, regex-based term substitution (a hardcoded EN→HU glossary of ~80 structural terms like "Parameters," "Returns," heading labels). `translatesProse = false`. This is the **default** adapter and is what CI actually runs.
- **`AiTranslationAdapter`** (`docs/scripts/api-translation.ts:328`) — shells out to a **CLI tool**, not a hosted API. It spawns `claude -p` (or a configurable command via `DOCS_TRANSLATION_COMMAND`/`_ARGS`) via `spawnPrompt()` in `tools/translation-adapters/src/index.ts:44`, writes the prompt to stdin, and parses JSON out of stdout. No `ANTHROPIC_API_KEY` or SDK call anywhere — confirmed by grep, zero hits for `ANTHROPIC_API_KEY`/`OPENAI_API_KEY`/`DEEPL` in the whole translation stack. There's also an `agy-wrapper.sh` (`tools/translation-adapters/agy-wrapper.sh`) that adapts the same stdin interface to an internal Anthropic CLI called `agy` (github.com/anthropics/agy), selected via `DOCS_TRANSLATION_COMMAND`.
- Adapter selection is via `DOCS_TRANSLATION_ADAPTER` env var (`glossary` default, `ai` to enable real translation) — see `createTranslationAdapter()` at `docs/scripts/api-translation.ts:468`.

Caching: `TranslationMemory` (docs facade, wrapping the shared `SharedTranslationMemory` class in `tools/translation-adapters/src/index.ts:97`) keys each unit by `sha256(kind + "\0" + sourceText)` and persists to committed JSON files under `docs/i18n-cache/*.json`. Unchanged source text is served from cache; only new/edited text reaches the adapter. This is genuinely incremental, human-run, and committed-cache-based, matching your memory's framing — just with a `claude`/`agy` CLI spawn as the "AI API," not a hosted API call.

**Key correction to your memory:** there is no "claude-code" vs "glossary" adapter split by guides-vs-API. Both `translate-guides.ts` and `build-api-locales.ts` call the *same* `createTranslationAdapter()` factory (selectable `glossary`/`ai`). The real split in `build-api-locales.ts` is structural: headings/badges/table labels *always* go through `GlossaryTranslationAdapter` (deterministic, never cached as "translated"), while prose blocks go through whichever adapter is selected via `DOCS_TRANSLATION_ADAPTER`.

## 3. A generic, non-VitePress translate module — yes, and it's not the one you were thinking of

`docs/scripts/translation-memory.ts` is *not* independently importable for this purpose — its `TranslationUnit` kinds (`"markdown" | "text" | "prose"`) and its adapter contract (`translateMarkdown`, `translateText`, `translateBatch`) are specific to the docs/VitePress content model, and `api-translation.ts`'s adapters hardcode "Translate ... from English to Hungarian" in their prompts.

But there's a **separate, genuinely generic pipeline** built for exactly your use case: `/Users/dwahl/Scripts/pantoken/packages/i18n/`. It exists to translate short UI-string key/value sets (originally for `@pantoken/web-components`) into 45 Canvas-parity BCP47 locales, and it's designed for auto-discovery across the monorepo:

- **`packages/i18n/scripts/lib/discover-sources.ts`** — `discoverStringSources(monoRoot)` walks every workspace package (globs read from `pnpm-workspace.yaml`) and treats **any package with a `src/i18n.json`** as a string source. Comment right in the file: *"Any package in the monorepo whose `src/i18n.json` exists is automatically included as a string source."* Today only one exists: `renderers/web-components/src/i18n.json` (a flat `{ "prevMonth": "Previous month", ... }` map, 7 keys).
- **`packages/i18n/scripts/lib/keys.ts`** — merges all discovered `src/i18n.json` files into `ENGLISH_SOURCES`/`TRANSLATABLE_KEYS`, with `keyFor(stringKey, englishValue)` hashing (note: hardcodes a `"wc\0"` namespace prefix — a residue from being built for web-components only, but harmless as long as keys are unique across contributing packages).
- **`packages/i18n/scripts/lib/translation-adapter.ts`** — a parallel, JSON-key-value-only adapter interface (`translateBatch(items, locale, localeLabel, onChunk)`), with the same `glossary` (passthrough, CI-safe) / `ai` (shells out to `claude -p` or `agy`, via `I18N_TRANSLATION_ADAPTER`/`I18N_TRANSLATION_COMMAND`) split as docs, but its AI prompt is generic UI-string phrasing ("Translate these UI strings from English into {locale}..."), not markdown-specific.
- **`packages/i18n/scripts/translate-bundles.ts`** — the driver: for each locale, finds cache misses, calls `adapter.translateBatch`, writes to `packages/i18n/i18n-cache/{locale}.json`.
- **`packages/i18n/scripts/build-bundles.ts`** — pure offline codegen: reads the committed `i18n-cache/*.json` and `ENGLISH_SOURCES`, writes `src/locales/{locale}.ts` files exporting `LocaleBundle` objects (`defineBundle({ locale, dir, label, strings: makeStrings(...) })`). **No network, no adapter, just local file reads/writes** — this is the `generate` package.json script.

**This directly answers your Q3**: if `packages/scaffold` added its own `packages/scaffold/src/i18n.json` with CLI prompt/help/error strings, `discoverStringSources` would pick it up automatically (scaffold is in the workspace globs), and `pnpm --filter @pantoken/i18n run translate` / `run generate` would translate and codegen it into the existing 45-locale set, for free, with zero changes to `packages/i18n` itself — just adding the JSON file and giving the keys unique names. You would *not* need to import anything from `packages/i18n` into `packages/scaffold`; you'd consume the generated output (or replicate the same generic pattern locally in scaffold if you want the strings to live and version inside the scaffold package itself rather than centralized in `packages/i18n`'s output).

## 5. What triggers translation generation, and network/key requirements

Docs (`docs/package.json` scripts):
- `docs:build` (the default CI path) → `docs:api:locales` (`node scripts/build-api-locales.ts`, no env override) → **default `glossary` adapter, no network, no CLI needed**.
- `docs:build:claude` → sets `DOCS_TRANSLATION_ADAPTER=ai` and `DOCS_TRANSLATION_COMMAND_ARGS="--model claude-haiku-4-5-20251001 ..."` → requires a working, authenticated `claude` CLI on the machine running the build (not an API key env var).
- `docs:locales:translate` / `:agy` — manual, human-run commands (`vp run docs:guides:locales:claude &amp;&amp; vp run docs:api:locales:claude`), explicitly documented in `translate-guides.ts`'s header comment as "a manual workflow — guide translations are committed, not regenerated on every build."
- `docs:check:locales` / `docs:check:drift` — parity/drift checks that run in normal CI without needing the AI adapter.

i18n package (`packages/i18n/package.json` scripts):
- `generate` (`node scripts/build-bundles.ts`) — **fully offline**, reads committed cache JSON only. This is the direct analog to scaffold's existing offline `vp run generate`.
- `translate` / `translate:agy` — manual, sets `I18N_TRANSLATION_ADAPTER=ai`, requires `claude` or `agy` CLI.
- `check:drift` (`check-bundle-drift.ts`) — explicitly documented as "Safe to run without AI credentials — no network required," runs in CI (an `i18n-drift` workflow job per its own comment) to fail fast if English source strings have no corresponding cache entry, forcing a human to run `translate` locally and commit the result.

**Implication for scaffold's `vp run generate`:** if you follow the `packages/i18n` pattern, scaffold's *existing offline* `generate` step stays offline — you'd add a parallel, separate, manually-invoked `translate` step (network + CLI-dependent) that only updates a committed cache file, and `generate` would keep just reading that cache, same as today. You would not be making scaffold's routine codegen depend on network access.
