[[PLAN]] The plan’s biggest problem is that the native adapters can’t “reuse existing Pantoken renderers”, because there aren’t any to reuse. Otherwise the structure holds up.

### Blocking
**1. Flutter, SwiftUI, and Compose have no component renderers.**

- `platforms/flutter`, `platforms/swift`, and `platforms/compose` each contain a single src/index.ts. They generate token constants (see the compose README: “numeric constants… reference them straight from composables”).
- Steps 3 and 5 and the “complete coverage” decision assume there’s something to wrap, and there isn’t.
- “Cover every component on every client” would mean writing and maintaining native Pantoken UI kits in Dart, Swift, and Kotlin. That’s a large new product, and it contradicts the stated “no duplicate implementations” goal.
- Decision for you: either (a) scope v1 to web, which covers React, Lit, and Angular through the web-component bridge, and ship native catalog-schema support only, or (b) make the native kits an explicit separate project.
- Recommendation: (a). On native, agents would use the Basic Catalog themed by the existing token output, which is what `use-a2ui` does today. The catalog JSON stays client-agnostic, and the coverage matrix marks native as “schema only”.

### Should fix
**2. Verify the A2UI facts before you commit to the design.** The plan states the Universal Web Components contract, the six-SDK list, and “extend the Basic Catalog” as fact. A pre-implementation check should confirm:

- Whether Universal Web Components actually register across React, Lit, and Angular in the shipped SDK versions.
- Which protocol versions each SDK supports. The current skill targets v1.0, and the plan hedges “verify each SDK’s status”.
- Whether catalogs can extend the Basic Catalog by reference or must copy it.
Make this a gating step zero with a written finding. The bridge design depends on the answers.

**3. Step 2 understates schema generation.** `formats/components` records are CSS-oriented (modifiers, aliases, `@scope`). A2UI components need typed props, child slots, and events. Part of that is likely missing, and the plan only says “add metadata where needed”. Spike two or three components first (for example Button, Tabs, Tooltip) to see how much new canonical metadata you need. Then adjust the scope and the coverage claim.

**4. Security belongs up front, not in step 7.** A catalog lets an LLM drive the UI, which gives you new input surfaces:

- Agent-supplied icon names, URLs, and HTML or slot content.
- Actions and functions that fire events.
- Attribute-to-property mapping on custom elements, which risks `innerHTML` or `href` injection.
Define an allowlist-only prop schema, ban raw HTML props, and add negative tests, before building the bridge. That also fits the Node-free runtime rule in `CLAUDE.md` for `@pantoken/web-components`.

**5. The bridge could import server-only packages.** The thin adapter lives in `renderers/web-components`, so it must not pull in `@cssdoc/*` or the generator. Say so in the plan, and keep the generator in `ai/` as a build script only.

### Smaller notes

- **Versioning.** Define the `catalogId` scheme and what counts as a breaking change. Removing a component or prop is breaking; adding one is additive. Without this, agents holding an old catalog break silently.
- **Drift gate.** You have the instui upgrade pipeline and a deprecation ledger. Tie catalog regeneration to them so an upstream bump can’t change the catalog without a version bump.
- **Docs browser.** Reusing the shadcn browser’s search patterns is fine. Drop “registration snippets” for native clients, since there’s no native registration to show.
- **Tests and evals.** Add negative evals (an agent inventing a non-catalog component), not only routing. The existing `use-a2ui` evals cover token theming, so keep those routing cases to avoid regressions.
- **Skill update.** The current `use-a2ui` skill says to use a custom catalog “only when the user explicitly requests one”. Revise that sentence deliberately once the catalog ships, or agents will keep ignoring it.
- **Sequencing.** The plan is one big change across about eight areas. Split it into milestones, each independently shippable with its own changeset: (1) verification and schema spike, (2) catalog source and generator, (3) web bridge, (4) docs browser, (5) native, if it’s still in scope.
- **Housekeeping.** The last line says the checkout is `main` with no changes, but you’re on `a2ui` with two commits already. The plan should record that those commits cover the skill and guidance only.
