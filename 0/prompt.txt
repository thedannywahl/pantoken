## 2. What a "record" looks like

Two authoring styles converge on one `Definition` shape.

**TS-authored record** (e.g. `/Users/dwahl/Scripts/pantoken/formats/components/src/components/button.ts`): calls `defineComponent({ name, css: (p) =&gt; css`…` })`, where `css` is an identity tagged-template and `${p}` is the prefix. The cssdoc doc comment is the leading `/** … */` inside the template.

**CSS-authored record** (the majority, e.g. `tree-browser.css`): a real `.css` file where the class prefix is written as the sentinel `.pfx-` (`/Users/dwahl/Scripts/pantoken/formats/components/src/lib/sentinel.ts`). A thin `.ts` wrapper wires it up — `/Users/dwahl/Scripts/pantoken/formats/components/src/components/tree-browser.ts`:
```ts
export const treeBrowser = defineComponent({
  name: "tree-browser",
  css: (p) =&gt; treeBrowserRaw.replaceAll(SENTINEL, p),
});
export const treeBrowserCss = treeBrowser.css;
```
`SENTINEL = "pfx-"` (chosen because it never collides with `--instui-*` tokens, `--pantoken-*` custom props, or `pantoken-*` keyframes, keeps a valid `.alert` when the prefix is dropped, and — being lowercase-first — makes cssdoc treat it exactly like the real `instui-` prefix so the source `.css` lints).

**The compose core** — `/Users/dwahl/Scripts/pantoken/formats/components/src/lib/define.ts`. `defineComponent`/`defineUtility`/`defineRule`/`defineDeclaration` all call `make(kind, input)`, returning a `Definition`:
- `name`, `kind`
- `rules(prefix, options)` — doc block + CSS body, what the aggregator concatenates
- `css(options)` — the standalone header-wrapped sheet, what `xxxCss` returns

`make()` splits the leading doc comment from the body (`splitLeadingDocComment`), then per-record appends alias twins to the **body only** (never the comment, so the alias post-processors' brace scanners don't see `{@link …}` braces).

**Variants/modifiers/aliases** are declared in the cssdoc comment and mirrored in selectors:
- **Modifiers**: `@modifier -color-secondary — A lower-emphasis secondary action.` matched by a `.-color-secondary` selector.
- **Size aliases** (`src/lib/aliases.ts`): `withSizeAliases` auto-appends long-form twins (`.-size-sm` → `.-size-small`) and `withSizeAliasDocs` adds the matching `@modifier -size-small` line so the twin isn't undocumented.
- **Deprecated aliases**: authored as metadata, e.g. in `alert.css`: `@modifier -has-shadow-false — @deprecated {@link -without-shadow}`. `deprecatedAliasPairs` regex-scans the comment (deliberately avoiding importing `@cssdoc/core`/postcss into the runtime bundle), and `withAliases` clones the canonical rule under the alias name with an `/* alias of … */` note.

**`@scope`** refers to the CSS `@scope` at-rule that many records use to contain their descendant styles. Example from `/Users/dwahl/Scripts/pantoken/formats/components/src/components/tabs.css`:
```css
@scope (.pfx-tabs) {
  :scope &gt; .list { display: flex; width: 100%; flex-flow: row wrap; }
  .tab { appearance: none; … }
}
```
These records carry a `@compat` note (e.g. `@compat Contains its element styles with the CSS @scope at-rule; needs a recent Chromium, Firefox, or Safari.`). Separately, the `prose` rule (`src/rules/prose.ts`) is parameterized by a `scope` **selector** option (default `.pantoken-prose`) rather than a class prefix.

## 3. The robust cssdoc declarations, including `@structure`

The cssdoc comment is the load-bearing metadata. Across `src/components/*.ts`+`.css`, the tags in use are: `@component`/`@utility`, `@summary`, `@remarks`, `@modifier`, `@part`, `@slot`, `@pseudo`, `@cssstate`, `@cssproperty`, `@a11y`/`@accessibility`, `@example`, `@structure`, `@related`, `@supports`/`@compat`, `@demo`. **28 records carry a `@structure` block.**

`@structure` captures the **DOM/element hierarchy** as a nested, selector-shaped tree (elements, classes, attribute selectors, `:optional` markers). The root `cssdoc.jsonc` config (`/Users/dwahl/Scripts/pantoken/cssdoc.jsonc`) lists `structure` in `render.sectionOrder` and sets `"structureView": "both"`.

Concrete example — `tree-browser.css` (lines 39–53):
```
 * @structure
 * .pfx-tree-browser {
 *   details {
 *     summary {
 *       [class*="-icon-"]:optional {}
 *     }
 *     ul {
 *       li {
 *         .item {
 *           [class*="-icon-"]:optional {}
 *         }
 *       }
 *     }
 *   }
 * }
```
It pairs with a full `@example` DOM sample, `@part .item`, `@pseudo ::before`, `@cssstate open`, and `@a11y` roles.

A part/panel example — `tabs.css`:
```
 * @part .list — The row of tabs.
 * @part .tab — A single tab; `-selected` marks the active one.
 * @part .panel — The content panel for a tab.
 …
 * @structure
 * .pfx-tabs {
 *   .list {
 *     .tab {}
 *   }
 *   .panel {}
 * }
```

A slot + custom-property example — `alert.css`:
```
 * @slot content — The alert's message content; may include a dismiss button.
 * @cssproperty --pantoken-alert-glyph &lt;url&gt; — The low-level status-glyph source; `-icon-&lt;name&gt;` sets it for you.
 * @cssproperty --pantoken-alert-icon-bg &lt;color&gt; — The coloured status-bar fill behind the glyph.
 …
 * @structure
 * .pfx-alert {
 *   slot {}
 *   .pfx-close-button:optional {}
 * }
```
Note `@structure` can name **sibling records** by class (`.pfx-close-button`) — which is why the scoped `cssdoc.jsonc` adds a `providers` entry (`./src/generated/_records.css`) so single-file linting can resolve cross-record references.

## 4. How CSS is generated/emitted

Two-stage pipeline:

**Stage 1 — `.css` → TS consts** (`scripts/component-styles.ts`): reads every `src/{components,utilities,rules}/*.css`, runs each through postcss with the `themeCustomMedia({ theme })` plugin for all three themes (`rebrand`, `canvas`, `canvasHighContrast`), and writes `src/generated/component-styles.ts` as `export const treeBrowserByTheme = {…} as const;` + `export const treeBrowser = treeBrowserByTheme.rebrand;`. Doc comments are **retained verbatim** (they flow into the CSS-API docs). Rolldown can't resolve Vite's `?raw`, so a generated `.ts` module is how the CSS text reaches the published bundle.

**Stage 2 — records → sheets** (`scripts/generate.ts`): calls `componentsCss({ prefix: "instui" })` etc. and writes `generated/base.css`, `components.css`, `prose.css`, `utilities.css`, `fonts.css`, `select.css`, `icons.css`. It also derives `component-icons.css` by regex-scanning the emitted sheet for `var(--instui-icon-*)` references and valuing them from the token IR, and writes the internal `src/generated/_records.css` at the `pfx` prefix (the cssdoc providers index — carries every record including the TS holdouts).

`componentsCss` (in `src/index.ts`) is a plain concat of `COMPONENTS.map(d =&gt; d.rules(ns(prefix), options).trim())` in the registry's exact, load-bearing order.

**Final emitted CSS** — the comment survives, `pfx-`/`${p}` becomes `instui-`, and alias-twin `@modifier` lines are appended. From `generated/tree-browser.css`:
```css
/* InstUI tree-browser (@pantoken/components) — prefix: instui */
/**
 * @component tree-browser
 …
 * @structure
 * .instui-tree-browser { details { summary { [class*="-icon-"]:optional {} } … } }
 * @related menu — Both present nested, selectable entries.
 * @modifier -size-small — Small. Long-form alias of `-size-sm`.
 * @modifier -size-large — Large. Long-form alias of `-size-lg`.
 */
.instui-tree-browser {
  border-radius: var(--instui-component-tree-browser-border-radius);
  …
}
```

## 6. How a component maps to InstUI values

The mapping is **entirely through token references**, not any code-level reference to upstream InstUI React components. Every declaration reads `var(--instui-component-&lt;name&gt;-…)` custom properties supplied by the `@pantoken/tokens` package (the InstUI token IR). Examples from `alert.css`: `var(--instui-component-alert-background)`, `var(--instui-component-alert-info-border-color)`, `var(--instui-component-alert-content-padding-horizontal)`; from `button.ts`: `var(--instui-component-base-button-medium-height)`, `var(--instui-color-background-interactive-action-primary-base)`.

So a component's "InstUI values" come from the `--instui-component-&lt;component&gt;-*` and `--instui-color-*`/`--instui-spacing-*` token families, resolved per theme at build time via `@pantoken/plugin-theme-custom-media`. `validate()` enforces that every referenced token actually exists in the IR, so the library tracks InstUI purely through the tokens. The only place InstUI is referenced by *name* is in prose/comments (e.g. button.ts explains "InstUI's `withBackground={false}`", "InstUI's ai-primary technique") and in the AI glyph mask sourced from `@instructure/ui-icons` — these are documentation, not runtime dependencies. There is no import of any `@instructure/ui-*` package in `src/` (they're mentioned in the README only as the alternative for real interactive components).
